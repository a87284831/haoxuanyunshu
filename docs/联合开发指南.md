## 1. 铁律（违反任何一条都可能造成生产事故）

1. **禁止在生产服务器上直接改代码**（包括"临时改一行试试"）。生产只接受来自仓库的部署。
2. **禁止在生产服务器上执行 `npm run build`**。前端构建只在本地/CI 进行。
3. **数据库结构变更只允许走 migration**。禁止在生产手工 `ALTER TABLE`。新表/新列 = 一个 migration 文件 + PR 一起评审。
4. **真实薪资/人员数据不入库**：工资表 xlsx、含身份证/手机号的导出文件，一律不得提交。`/*.xlsx` 已在 .gitignore，提交前 `git status` 自查。
5. **`.env` 不入库、不通过聊天工具传完整内容**。缺配置找管理员当面/电话要。
6. **数据库获取失败必须显式报错**，禁止静默降级按 0 计算（薪酬系统红线）。

## 2. 日常开发流程

```bash
# ① 每次开发前（必做）
git checkout main
git pull origin main

# ② 开功能分支（一个功能/修复一个分支，命名见第 3 节）
git checkout -b feat/xxx

# ③ 本地开发 + 测试（必跑，CI 会再跑一遍，挂了不许合并）
php vendor/bin/phpunit
cd frontend && npm run test && npm run build && cd ..

# ④ 提交（提交信息规范见第 3 节）并推送
git push origin feat/xxx

# ⑤ GitHub 提 PR：base=main
#    - PR 页面会清晰列出全部改动，review 在这里进行
#    - CI（phpunit + vitest + build）绿了才能合并
# ⑥ 合并后删除功能分支（GitHub 页面一键删）
```

**每天下班前**：把当天的分支 push 上去（哪怕没做完），让协作者能看到进度、避免撞车。

**pull 遇到冲突**：只有改了同一文件同一区域才会发生。git 会用 `<<<<<<<` 标记双方改动，保留正确的、删标记、提交。解决不了就截图发对方一起定。

## 3. 分支与提交规范

### 分支命名

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/hq-coef-dialog` |
| `fix/` | 缺陷修复 | `fix/purchase-qty-zero` |
| `chore/` | 构建/工具/清理 | `chore/remove-public-app` |
| `docs/` | 纯文档 | `docs/handover-update` |

### 提交信息

一行中文主题（≤ 50 字）+ 空行 + 必要说明。类型前缀与分支一致：

```
fix: 采购数量0被误放行——恢复必填拦截

- validateRow 恢复原语义（0/空均拦截；库存0合法）
- 同步 fillLogic/FillForm.regression 测试
```

历史风格参照 `git log --oneline -20`。**禁止** `update`、`改bug`、`111` 这类无信息提交。

## 5. 数据库变更流程

```bash
php artisan make:migration add_xxx_to_yyy
# 编写 up()/down()，本地 migrate + migrate:rollback 各验证一次
```

- PR 必须包含 migration 文件，review 重点看 `down()` 是否可回滚
- 生产执行：部署时 `php artisan migrate --force`，**只允许该命令改生产结构**
- 历史教训：`custom_reviewed` 列曾手工加在生产、迁移未登记，造成 schema drift（2026-10-21 已补记）

## 6. 部署流程（指定人员执行）

| 项 | 约定 |
|---|---|
| 谁部署 | 合并 PR 的人 / 或约定固定一人，群里报备"开始部署" |
| 部署源 | **只从 `main` 分支**构建部署，禁止从功能分支部署 |
| 前端 | `deploy/deploy-frontend-full.sh`：整包同步 + 引用资源自检 + 不过 200 自动回滚 index.html |
| 后端 | 快照 → scp PHP 文件 → `migrate --force`（如有迁移）→ `config:cache` 重建 → 冒烟 |
| 构建产物 | `public/app` **不入库**，谁部署谁从 main 本地 build |
| 回滚 | 部署前快照在 `/root/pre_deploy_*`；数据库快照每日 03:00 自动 |

**部署后必做**：在群里发"已部署 <commit 短哈希>"，协作者据此确认自己 PR 是否上线。
