### 2026-09-30 版本 45a0693（docs）｜ 钉钉同步机制全面评估
- 功能点：对钉钉同步代码做全面审计，识别 7 项问题与改进建议，尚未改码
- 涉及文件（审计对象）：`app/Services/DingtalkService.php`（token 获取/缓存 L49-89、API 调用 L91-123、全量数据获取 L125-260、花名册 L264-305、配置管理 L330-375）、`app/Http/Controllers/Api/DingtalkCallbackController.php`（手动同步 L63-108、回调处理 L110-145、全量同步主流程 L148-274、单人员同步 L369-440、花名册映射 L443-480）、`routes/console.php`（cron 每日 02:00 + withoutOverlapping + onOneServer）
- 审计结论：
  - P0（必须修）：回调 `handle()` 未验证钉钉签名——任何人可伪造事件篡改人员状态（当前回调未注册，暂不暴露）
  - P1-1：`runFullSync()` 无事务包裹——中途失败留不一致窗口（全量幂等可重跑修复，但中间态有风险）
  - P1-2：`getAccessToken()` 失败无重试——网络抖动导致整次同步白跑
  - P1-3：回调 `handleUserChange` 每次都全量拉部门树——单回调触发全量 API，性能浪费
  - P2-1：离职人员 `person_type` 硬编码 `staff`——管理人员离职被错误标记
  - P2-2：花名册 `array_merge` 不删旧值——钉钉端删字段值后本地残留
  - P2-3：同名匹配兜底（`name + project_name`）——同项目同名有错误合并风险

### 2026-10-22 CPU 99.5% 白屏事故根因 + 全链路加固（8d6d647）——已部署
- **现象**：用户反映网站白屏；SSH 22/8728 端口超时；HTTP/HTTPS TCP 握手成功但请求超时。阿里云控制台 CPU 99.5%。用户手动重启服务器后恢复。
- **根因（三层叠加）**：
  1. `CACHE_STORE=database` 但生产 config 缓存残留 SQLite 配置 → Laravel fallback 用本地 SQLite，`Cache::lock()` 完全失效。钉钉同步 schedule 虽写了 `withoutOverlapping()`，但锁靠 cache 驱动，锁失效 = 没锁。
  2. 钉钉同步每次跑 **240 秒**（拉 1422 人花名册），但 cron `schedule:run` **每分钟触发一次**。无锁 → 上一个没跑完，下一个新进程又启动 → **N 个同步并发**，全在抢 MySQL + CPU。
  3. 2 核 1.6G 机器，php-fpm pm.max_children=5，加上多个同步进程 → CPU 99.5% → nginx/php-fpm/sshd 全都抢不到时间片 → 表现为"TCP 能连上但不回包"。
- **关键证据**：钉钉同步日志里连续出现 4 次 full sync（每次都跑 240s），journalctl 没有任何 segfault/OOM 记录，说明不是宕机是被吃死。
- **修复（三重保险）**：
  | 层 | 措施 | 说明 |
  |---|---|---|
  | 代码 | `DingtalkSyncCommand` 加 **flock(LOCK_EX\|LOCK_NB)** 文件锁兜底 | 不依赖 Laravel cache，是操作系统级锁。与 `schedule::withoutOverlapping()` 双保险。并发跑 3 个同步只会成功一个，另外两个秒退。 |
  | .env | `CACHE_STORE=database` → **file**；`QUEUE_CONNECTION=database` → **sync** | file cache 用本地文件，永远不会因 DB/配置问题失效。项目未走 Laravel 队列，sync 同步执行省掉一个 DB 依赖。 |
  | 运维 | CPU watchdog `/usr/local/bin/cpu-watchdog.sh` + cron 每分钟跑 | 持续监测 CPU，**>90% 且连续 10 次** → `kill -9` 最占 CPU 的 3 个进程 + `systemctl restart php8.2-fpm nginx`。 |
- **配套加固**：
  - MySQL 慢查询日志开启，`long_query_time` 从 10s → **2s**（写入 `/var/lib/mysql/*-slow.log`）
  - `.env`/`storage`/`bootstrap/cache` 权限修正为 `www-data:www-data`（之前 root:root 640 导致 php-fpm 读不到，靠 config 缓存掩盖，部署时 `optimize:clear` 会暴露）
  - 重建 config 缓存
- **验证**：phpunit 362/362，站点 200，watchdog cron 有日志，MySQL 慢查询 ON。
- **教训**：`withoutOverlapping()` 依赖 cache 驱动是隐含前提；生产 `.env` 权限不能 root:root 640；crontab 高负载命令必须在命令内部再做硬件级锁，不能只信框架层的软锁。
